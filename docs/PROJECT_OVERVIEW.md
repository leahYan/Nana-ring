# Project Ring Health: POC Overview

## 1. Executive Summary

The Ring Health system is a persistent data pipeline for health metrics generated by smart rings. It bridges the hardware data to a private, secure cloud environment (Supabase/Hostinger) for long-term storage and analysis.

> **IMPORTANT — Definition of "POC":** This project is a limited-scope but **fully functional** system that captures **real data from a physical smart ring**. "POC" means reduced features and a small user base — it does **NOT** mean simulated hardware, fake BLE connections, or synthetic/mock health data. Every component must work end-to-end with the real ring hardware and SDK.

## 2. Implementation Constraints (Read First)

These rules apply to **all** components (Android, Backend, Frontend). Any AI agent or developer working on this project **must** follow them:

1. **No mock/fake data anywhere.** All health readings must originate from the physical smart ring via the provided SDK (`libs/ring_sdk_1.0.0.1.aar`). Never generate, randomise, hardcode, or simulate health metric values. Never create fake BLE scan results or simulated Bluetooth connections.
2. **No fake BLE/Bluetooth.** BLE scanning, pairing, and data retrieval must use the SDK's actual classes (e.g., `BleScannerHelper`, `BleOperateManager`, `MyBluetoothReceiver`). Do not create mock implementations of these classes.
3. **Graceful "no data" states.** When the ring is not connected or no data has been received, the app and dashboard must display appropriate empty/waiting states — never fall back to generating placeholder data.
4. **SDK is the single source of truth.** The `ring_data_dictionary.csv` defines every metric, its SDK field name, data type, and transformation. Implementations must read data from the SDK fields specified in that document. Do not invent alternative data sources.
5. **No demo/seed data scripts.** Do not create scripts that populate the database with fake readings for demonstration purposes. If a test environment needs data, it must come from the actual ring or be clearly documented as a separate, optional developer-only utility that is never part of the production codebase.

## 3. Core Architecture

Refer to `docs/system_architecture.png` for a visual map of the data flow.

- **Mobile Bridge:** Android App (Kotlin) using `libs/ring_sdk_1.0.0.1.aar`.
- **Cloud Backend:** FastAPI (Python) hosted on Hostinger VPS (Docker).
- **Database:** Supabase (Managed PostgreSQL) for time-series data.
- **Frontend:** React + TypeScript dashboard on Vercel.

## 4. Data Flow Philosophy (Offline-First)

1. **Ring -> Phone:** Raw BLE data received by the SDK. The SDK's callback interfaces (e.g., `StopHeartRateRsp`, `BloodOxygenEntity`, `SleepNewProtoResp`) deliver real measurements. The app must register listeners on these callbacks and persist whatever the SDK provides.
2. **Phone (Room):** Data must be persisted to Room SQLite _immediately_ upon receipt from SDK callbacks. Room entities must mirror the fields defined in `ring_data_dictionary.csv`.
3. **Phone -> Cloud:** Scheduled WorkManager tasks flush `pending_uploads` to the FastAPI backend when internet is available. The payload format is defined in the `api_batch_upload` section of the data dictionary.
4. **Cloud (Postgres):** Data is stored permanently in Supabase. Schema must match `ring_data_dictionary.csv` exactly.
5. **Web (Dashboard):** Fetches historical data from FastAPI for visualisation. Displays "Waiting for Data" when no records exist for the selected period.
